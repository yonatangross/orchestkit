4 major floor lags, investigated · 2026-07-31

Three were noise. The fourth needed a ceiling, not a bump.

Four libraries showed MAJOR-BEHIND. The obvious move was to raise all four floors. Checking each against its published type declarations instead: three were fine, and the one that mattered needed the opposite of a raise.

Why mcp is different

"Since pip install mcp now installs 2.x, keep a <2 upper bound on your requirement until you've migrated." — the MCP 2.0 README

Our floor was >=1.27.0, unbounded, so it resolves to 2.x today. Every Python snippet here is v1 (from mcp.server.fastmcp import FastMCP), and FastMCP appears zero times in the 2.0 README. Raising the floor would have made this worse; the fix is the ceiling upstream asks for.

A ceiling needs its own severity

Declaring >=1.28.0,<2.0.0 made the gate print MAJOR-BEHIND forever, which is the cry-wolf failure the comparator is written to avoid. So a declared bound now reports bounded and does not count as a lag.

>=1.28.0,<2.0.0  vs 2.0.0   -> bounded         (intentional)
>=1.28.0,<2.0.0  vs 1.30.0  -> minor-behind
>=1.27.0         vs 2.0.0   -> major-behind    (unbounded, unchanged)
>=11.0.0         vs 12.0.4  -> major-behind    (unchanged)
>=1.28.0,<=2.0.0 vs 2.0.0   -> major-behind    (inclusive bound, NOT excluded)
>=4.0.0          vs 3.0.0   -> unsatisfiable   (unchanged)

Two corrections I made mid-investigation

I first reported 5 testcontainers APIs absent in v12. That file was a one-line re-export; the real declarations live in postgresql-container.d.ts, where 4 of 5 were present. The 5th, withReuse, is on the base GenericContainer, which PostgreSqlContainer extends. Both readings were wrong, and both were caught by opening the file rather than trusting the grep.

The general lesson: MAJOR-BEHIND is mostly not a defect signal. A floor is satisfied by any newer release, so 3 of 4 flags were noise. The one real problem was invisible in that framing, because the danger was not a floor that was too low, it was a floor with no ceiling.
