Three false signals: free memory, the zsh loop, the silent rsync

Three diagnosis traps from one operator session, each with the rule that would have caught it. Evidence cited in the PR body.

1. Free percentage is not evidence (doctor guidance)

What the quick tool printed during a live load diagnosis:

memory_pressure 
System-wide memory free percentage: 84%
Diagnosis: the machine has memory to spare, so the load must be the app on screen. (This is the wrong culprit.)
the probes 
sysctl vm.swapusage
  vm.swapusage: total = 8192.0M
    used = 7065.6M  free = 1126.4M
vm_stat  (wire + compressor occupy the rest)
  59 of 64 GB in use

Swap nearly exhausted while "84% free" prints: the percentage answers a different question than "is the machine under memory pressure". Name a culprit only after a process tree confirms one.

2. The zsh one liner that never split (display-lint hook message)

A loop written as a shell one liner, run through the Bash tool:

set -- $spec
for url in "$@"; do fetch "$url"; done
zsh does not word split $var: the loop body runs ONCE with the whole spec string as one argument. Every fetch got one malformed URL. Five minutes of 404s.
bash splits $var on IFS: the loop body runs once per word, each iteration gets one well formed argument. Same one liner, different shell, different behaviour.

Rule: loops belong in bash script files, where the shell is the one you wrote. The ork display-lint advisory now says why: script files render as one short tool card, survive line wrap, and get real bash word splitting.

3. The rsync output that was not there (test guidance)

Dry run rsync on macOS (openrsync) vs CI (GNU rsync), parsed by a test:

Both dialects are silent without -v and wrap the file list in different banners. A test that parses rsync output must prove itself on both; the safe subset is plain filename lines, which is what the #4079 ratchet test greps.
