error-analysis: from 100 traces to named failure modes

Interactive walkthrough of the new error-analysis skill (PR #4402). Evals-first failure analysis for LLM apps, the Husain and Shankar method: real traces in, binary evals out.

1. Sample real traces

Pull a default sample of 100 real traces from the Langfuse public API, or read an exported JSONL file. Keep the trace id and enough context to review each one.

langfuse api GET /api/public/traces?limit=100
traces.jsonl  (one trace per line, ids preserved)

2. Open-code each failing trace

One short free-form note per failing trace, written by the human. Claude drafts candidates; the human accepts or edits each one.

trace t-1042: draft note (Claude): "tool returned empty result set, model apologized instead of retrying"

Waiting for human decision.

3. Axial-code the notes

Claude proposes 5 to 8 named failure modes from the open notes. The human confirms the taxonomy before anything is written.

tool-empty-result context-drop wrong-schema over-refusal stale-param

4. Write failure-taxonomy.md

Each mode gets a definition, example trace ids, a count, and a binary eval decision. Counts table included.

ModeCountEval
tool-empty-result31yes
context-drop18yes
wrong-schema9yes
over-refusal3no
stale-param2no

5. Prompt or code? Replay the tool output

Before writing an eval, replay the tool or DB output for a trace. Correct output means a prompt or context failure. Wrong output means a code failure, and no eval will catch it.

Pick a replay outcome.

Evals only for named, recurring modes. Binary pass/fail, written critique on failure, judge aligned against human labels, then handed to the eval-runner agent.
