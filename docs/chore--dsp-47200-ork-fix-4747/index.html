Issue text stays away from tokens

Security fix for claude-triage.yml (#4747). The old workflow ran the model in one job that held id-token: write and the OAuth secret while issue text was in scope. The OIDC exchange can mint a write-scoped app token, and public attacks (Flatt Security, Microsoft, June 2026) hid instructions in HTML comments and invisible characters inside issue bodies.

Before: one job held everything

triage held id-token: writeCLAUDE_CODE_OAUTH_TOKEN while issue text entered the same job via github.event.issue. Two stale comments also claimed issues: write the job never had, and two github.event.issue reads were dead code on a dispatch-only trigger.

Lint verdict: FAIL. Untrusted text and credentials shared a job.

After: a three-job split

Click a job to see what it reads and what it holds. The lint rule: no job may do both.

What the model job cannot do

The triage job keeps only what it must hold: the OAuth token and a read-only GITHUB_TOKEN for two exact gh calls (label list, milestones). No id-token, no checkout, no Read/Grep/Glob tools, no issue number to look up. The only write in the whole workflow is issues: write in the comment job, which never sees the raw issue or the model token and posts the model output file verbatim.
