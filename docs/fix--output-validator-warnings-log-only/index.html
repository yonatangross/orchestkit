ORCHESTKIT LAB · FIX-OUTPUT-VALIDATOR-WARNINGS-LOG-ONLY

Warnings the User Never Sees

PR #4199 made output-validator read the real subagent result. That fixed the dead checks and woke up two of them: the short-output warning and the error-keyword warning (a result containing error, failed or exception) now fire on ordinary subagent stops, and both rode into systemMessage, straight to the user.

The operator decision

On a pass, warnings are log-only. The warnings go into the record the hook already writes (the === OUTPUT VALIDATION === log file), and systemMessage keeps the exact base line it had before #4199. On the failure path nothing changes: errors still append to systemMessage, and warnings still ride along after them.

before: systemMessage += ` | Warnings: ${validationWarnings.join('; ')}`; on every pass with a warning, shown to the user on ordinary stops.
after: the same text is written into the log record via warningsForLog; the pass message is the base line only.

Measured before the change (M4, git show 40181a09^): on a pass the base line was the whole message, because the warnings could not fire on real payloads while the hook read fields Claude Code never sends. Keeping the base line untouched restores that user-visible behaviour exactly.

Measure it yourself

Send the hook a short subagent result and compare where the warning lands.

last_assistant_message="Done." (5 chars) → short-output warning fires

Mutation check: putting the warnings back into systemMessage fails T-a and T-b along with the other log-only pins (20 failed | 32 passed of 52); restored, the file is 52 of 52 and the subagent-stop suite is 442 of 442.
