glyph: terminal width vs the 72-column non-TTY cap

Issue 4159. The glyph skill taught side-by-side key/value columns with no host awareness. The board below is the real output for one 5-row status fixture: 113 terminal columns. In a terminal that is fine. In a host that reflows text (CI logs, chat widgets, VS Code chat, web transcripts, agent desktops) the same bytes wrap at whatever the host gives them, and the wall on the right is what the reader gets.

Before: one render, two hosts

The right panel is not a different render: it is the same bytes with wrapping allowed, which is exactly what a non-terminal host does to them. Every box-drawing row folds, the two columns interleave, and the board becomes a wall.

After: the non-TTY surface caps at 72 columns

Rule 8 in the skill: read the surface from the environment the same way the skill already infers audience and surface. With a terminal (TTY), render as before. Without one, cap every diagram line at 72 columns and render key/value or comparison data as one narrow table or a vertical list, never side-by-side columns. The 12-line budget is unchanged, and TTY behaviour is unchanged.

Reproduce

bash scripts/render-ascii.sh key-value --mode wide < tests/fixtures/ascii/kv-glyph-5row.txt        # the 113-column board
bash scripts/render-ascii.sh key-value --width 72 < tests/fixtures/ascii/kv-glyph-5row.txt | cat   # piped (non-TTY): the narrow list
bash tests/unit/test-glyph-non-tty-width.sh   # the fixture gate: red at 113 before the fix, green at 51 after

Fixture: tests/fixtures/ascii/kv-glyph-5row.txt. Widths counted by tests/fixtures/ascii/display-width-oracle.py (east_asian_width W/F plus the closed status-glyph vocabulary, so emoji count as 2 columns).
