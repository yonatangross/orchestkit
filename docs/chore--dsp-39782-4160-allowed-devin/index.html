The rebuild guard that refused its own release stamp, and the one entry that fixes it

Issue #4173. One line in .github/workflows/release-please.yml: add \.devin-plugin/plugin\.json to the ALLOWED alternation. Release PR #4166 (10.0.0-beta.34) is blocked on it.

The defect, as a sequence

Release-please has an extra-files entry for .devin-plugin/plugin.json (.release-please-config.json, jsonpath $.version), so on the release branch it stamps the new version into that file. That is a legitimate difference from main: main sits at 10.0.0-beta.33, the release branch at 10.0.0-beta.34.

But the "Rebuild hook bundles on the release PR" step refuses to execute when the release branch differs from main outside the ALLOWED regex, and .devin-plugin/plugin.json was not in it. From release-please run 35062658242 at 06:13:04Z:

##[warning]Release branch release-please--branches--main differs from main
outside release-owned paths; refusing to execute its build:
.devin-plugin/plugin.json

Because the refusal is a ::warning, the job still reports success. The hook bundles are never rebuilt, and ci.yml's "Check hook bundles are release-owned" gate then blocks every release PR. Every release, forever, until the entry lands.

Why the fix is safe


The new entry is a full-path alternation member, \.devin-plugin/plugin\.json, anchored by the same ^(...)$ as its neighbours, so it cannot swallow nearby paths: README-notes.md still fails against README\.md, and hook sources under src/hooks/src/ still fail against src/hooks/dist/.*. The guard keeps catching genuine drift; it only stops catching the version stamp release-please itself writes.
