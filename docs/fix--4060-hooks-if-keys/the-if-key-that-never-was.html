HOOKS SCHEMA INVESTIGATION

Two if keys.
At the wrong level.

hooks.json fronted two hooks with an "if" key sitting on the matcher group: PreToolUse[7] (headless gate in front of headless-responder) and PermissionRequest[0] (an 11-rule dangerous-Bash gate in front of the unified-dispatcher). The CC hooks schema admits if on the hook command object only, so the loader reports both as unknown keys and ignores them at every session start.

The before and after shape

"PreToolUse": [
  -   "matcher": "AskUserQuestion",
  -   "if": "AskUserQuestion(*)",        # group level: unknown to CC, ignored
  +   "matcher": "AskUserQuestion",      # the group carries matcher + hooks
      "hooks": [ ... headless-responder, self-gated on headless mode ... ]
],
"PermissionRequest": [
  -   "matcher": "Bash",
  -   "if": "Bash(git push*) || ... || Bash(* | xargs rm *)",  # 11-rule chain
  +   "matcher": "Bash",                 # members self-gate dangerous input
      "hooks": [ ... unified-dispatcher, REJECT_PATTERNS + SECURITY_BLOCKLIST ... ]
]

Why CC ignores them

The hooks documentation defines the matcher group as carrying matcher and hooks. The if field is documented on the hook command object, introduced in whats-new 2026-w13, and admits "a single permission rule without logical operators; combining conditions requires separate hook handlers". Nothing in 2.1.264 to 2.1.268 touches the hook schema: 2.1.264 was never published, and the 2.1.268 row's only hook fix makes PermissionRequest hooks fire under -p. The 11-rule chain was unsupportable even at the documented level.

Blast radius: the removal widens the matcher

Removing the group keys WIDENS the Bash PermissionRequest matcher to all Bash.

Had the gate ever worked, the dispatcher would have judged only the 11 dangerous prefixes and every other Bash call would have bypassed the branch entirely: branchless approval, the behaviour the keys never shipped because the loader ignored them. The widening is the point: the auto-approver needs to front every Bash permission request, and the dispatcher's own self-gating (REJECT_PATTERNS, SECURITY_BLOCKLIST, compound-command rejection) is what makes fronting all Bash safe.

The widening also owns the re-add risk: on a future CC that starts supporting group-level if, re-adding the key would silently narrow the auto-approver back to the dangerous subset, safe commands would fall back to default approval, and every unit test would still pass against a control nobody is subject to. The self-gating of the members is the invariant that survives both directions.

This is an explanatory model, not a live test runner. Locally, the schema-keys suite failed before the fix and all 6 assertions passed afterward.
