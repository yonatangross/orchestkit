The watchdog that fired with the payload in the pipe

Under load, run-hook.mjs ran piped hooks on {} although every byte of the payload was already waiting in the pipe. The timer firing was read as proof the pipe was empty. One deferred loop turn fixes it; the 100ms window is not raised.

Why it happened

  • The runner arms setTimeout(100) before it attaches the stdin data listener, and libuv runs the timers phase before the poll phase.
  • A process starved of CPU for more than 100ms right after arming reaches the timer callback first. In every starved run the instrumented copy read all 76 bytes with readSync(0) at fire time, while readableLength was still 0: the stream had not polled yet.
  • So the hook ran on {} with a valid payload one poll away. For a piped scanner such as content-secret-scanner, that is a check that silently checks nothing.

The fix

  1. When the 100ms timer fires, defer once with setImmediate. The check phase runs after one poll, so anything already written is read.
  2. Only a pipe that is still empty after that poll takes the empty-payload path, with the same #3415 warning and the same #4678 fail-closed gates.
  3. The hang guard stays: a pipe that never delivers still runs on {}, one loop turn later than before. The PreToolUse budget is unchanged on every path that delivers input.

Not covered

  • A producer that really writes its first byte later than 100ms plus one loop turn still loses the race. That stays the #3415 warning; redirecting a file (#4769) is still the robust shape for tests.
  • The starvation rates by shape were measured on an instrumented copy of the runner with one hook key. The suite rows were measured on the real runner in this branch.
