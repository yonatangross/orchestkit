Two CI fixes in one PR

1. The weekly traffic snapshot has failed every run (3 of 3 scheduled runs, 14, 21 and 28 September) with HTTP 403 Resource not accessible by integration. 2. The release-please guard fired on PRs whose base is a release/* branch, a branch release-please never reads.

1. Traffic snapshot: which token reads traffic

The traffic endpoints need the repository permission Administration: read. GITHUB_TOKEN can never be granted it, whatever the workflow permissions: block says. A GitHub App installation token can, once the App has it.

2. Release-please guard: which base does it guard

release-please.yml runs on push to main only (plus its weekly cron and manual dispatch on main), so its state machine never reads a release/* branch. The guard now skips those bases with a notice. Every other base behaves exactly as before.

3. What changed

traffic-snapshot.ymlMints the Release Bot token (same App secrets and the same pinned create-github-app-token SHA as release-please.yml) scoped to administration:read, contents:write, pull-requests:write. A preflight step calls gh api repos/OWNER/REPO/traffic/views and fails with an error naming Administration: read. GITHUB_TOKEN drops to contents:read; the push and the PR use the App token, passed per command, never written to .git/config.
release-please-guard.ymlThe bot-check step exits with skip=true when github.base_ref starts with release/.
Checks runactionlint with the CI flags: clean. zizmor with the repo config: 0 low, 0 medium, 0 high. tests/ci/test-traffic-snapshot.sh: 27 of 27. tests/ci/test-workflow-step-fault-arms.sh: 28 of 28.
One operator action. Grant the OrchestKit Release Bot App the repository permission Administration: Read-only, then accept the updated permissions on its installation. Until then the preflight step fails with that exact instruction instead of a bare 403.
