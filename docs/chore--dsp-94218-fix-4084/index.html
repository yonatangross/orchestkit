The validator that dirtied the tree it validated

PR playground for #4084: the pre-commit test runner checked nothing and chmod'ed everything.

Every invocation of tests/run-all-tests.sh, including the one inside the pre-commit hook, opened with two find ... -exec chmod +x {} \; passes: one over tests/, one over src/hooks/. The intent was courtesy (a checkout that lost exec bits still runs), but a validator that writes is a validator that lies: whenever a tracked script sat in the index as mode 100644, the chmod flipped the on-disk bit, and git status picked up a mode change nobody asked for. That is exactly what happened to tests/test-ascii-density-ratchet.sh on lane fix-4070, whose commit then carried a mode change its author never saw.

Run the pre-commit path yourself

Pick the tracked mode of one script and which runner opens the run, then read what git status --porcelain says afterwards. 

find tests src/hooks -name "*.sh" -exec chmod +x {} \;

$ git status --porcelain

The fix: check, never mutate

The chmod passes are gone. In their place a read-only preflight, scoped by git rather than by find, so it sees exactly the tracked scripts (no node_modules, no scratch dirs, no sibling worktrees) and can never touch a byte: 

git ls-files -s -- '*.sh'   # one call, mode and path per line
# compliant = index records 100755 AND the exec bit is set on disk
# otherwise: fail the run and name the repair, per file:
#   fix: chmod +x <file> && git add <file>

Failing loudly instead of silently repairing is the point: the seven tracked scripts that sat at 100644 are fixed in this same PR, so the check is green on main, and any future 100644 script is a blocked commit with instructions, not a surprise mode change riding along in someone else's diff. Outside a git work tree (a tarball checkout) the check degrades to a skip, exactly like the old courtesy chmod did.

The ratchet that keeps it honest

tests/ci/test-run-all-tests-no-mutation.sh builds a throwaway git repo whose only tracked script is a copy of the runner, then drives the same --lint invocation the pre-commit hook makes:

scenarioasserts
clean fixturerun exits 0 and git status --porcelain is empty afterwards (the mutation regression, caught)
exec bit strippedrun exits non-zero, names the file and the fix, and the file is still not executable afterwards (no silent repair)
index mode 100644run exits non-zero, names the fix, and the index is still 100644 afterwards

The fixture has no test directories, so every lint category SKIPs and the exit code carries only the preflight verdict. Git environment variables (GIT_INDEX_FILE and friends) are scrubbed with the same env -u list the pre-commit hook uses (#3822), so the fixture's git calls can never write through to a real index.

Reproduce it

bash tests/ci/test-run-all-tests-no-mutation.sh
bash tests/run-all-tests.sh --quick
git status --porcelain   # empty: the run left the tree exactly as it found it
A pre-commit hook sees your tree at its most fragile moment, the second before history is written. Its first job is to leave that moment untouched. #4084 makes the runner keep that promise and prove it every run.
