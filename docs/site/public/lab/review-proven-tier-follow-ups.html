Four follow-ups on the proven-by-a-run tier of the PR review

The review script labels a critical or high finding proven only when it carries the command it ran, its output and the output the intent requires. A review of that tier found four small points about how honest the label reads. Each one has a test that fails on the base commit and passes here.

1 / The result says whether runs were allowed

Runs are off unless the caller sets allowRuns to true. With runs off the reviewers are told to run read-only commands only, so a command, output and required output they fill in is a read, not a run of the code. Before, it could still be labelled proven.

Before

Now

The result carries allowRuns and a separate proof.unverified list. Verdicts, refuter votes and spawn counts are the same either way; only the label changes.

2 / One rule for re-running a proven command

Step 5 of SKILL.md said to re-run a proven finding's command before quoting its output as seen, while two other places say the skill's own post gate denies local tests and builds. All three now say the same: a command the gate denies is quoted as the reviewer's claim, not as seen, unless it was re-run read-only. A test pins the sentence in all three places and the old wording out of step 5.

3 / The zero-width strip is written as escapes

The check that strips invisible characters before testing for real text held the characters themselves, which an editor can drop without a sign. It is now the range of escapes (U+200B to U+200D and U+FEFF). A test fails if the script holds any literal invisible character, and another shows an invisible prefix cannot turn a placeholder such as n/a into a command.

4 / The word null counts when the intent names it

The placeholder check refused an output that was exactly null, None, undefined or empty, so a defect whose proof is "printed null" could never be proven. Now such a word counts as output when the required output names the same word. Every other placeholder stays refused, even when named.

Not shown here

No real, non-stubbed proven finding exists yet, and whether the skill's own gate also binds the reviewers the workflow spawns is not answered here: if it does, a run of a test is denied and a proven finding can only hold read-only commands. The review page of the skill is now generated as a folder because it crossed the page size cap; that is a build effect, not a content change.
