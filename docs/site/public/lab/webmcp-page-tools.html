Mentioned only, until it was registered

ora.ai's usability check scored the docs site 0/5 on "webmcp" with the verdict mentioned only, not implemented. The site did register tools, but only through navigator.modelContext.provideContext() inside a client useEffect, and the served HTML carried nothing about them except a sentence of prose. PR #4107 moves registration to document.modelContext.registerTool() first (navigator surfaces as trailing fallbacks), adds a get_page tool, and renders a declarative <form toolname="search_docs"> on the homepage so a crawler that never runs JavaScript still finds a real tool. This page mocks the browser API so you can see what an agent now gets.

What a browser exposes decides which surface gets the tools

The helper feature-detects in order and stops at the first surface that exists, so a browser shipping both never sees a tool registered twice. Pick a browser shape and watch where the four tools land:

tooldescriptioninput schema
These four objects are the same shape the site registers from docs/site/lib/webmcp-tools.ts: name, description, JSON-schema input, and an execute function backed by an existing route.

Call search_docs

The tool's execute function builds one GET against the site's unified search route. Type a query, pick an optional content-type tag, and read the request shape. When this page is served from the docs origin the call actually runs; from a file or another host it stops at the shape.


    

    

  


  
Before and after: the provider

  
Before, the whole provider was one call on one surface behind one feature check. After, the component is a shim and the ordering lives in a React-free helper the unit test can drive with a mocked document.

  

    

      
before webmcp-provider.tsx (lines 116 to 122)


useEffect(() => {
  const ctx = (navigator as Navigator & { modelContext?: ModelContext })
    .modelContext;
  if (!ctx?.provideContext) return;
  ctx.provideContext({ tools: TOOLS });
}, []);

      No document.modelContext, no registerTool, and nothing in server HTML. A checker reading the current spec shape found no registration; a checker reading raw HTML found a sentence.
    

    

      
after lib/webmcp-tools.ts registerWebMcpTools()


const docCtx = (doc as HasModelContext).modelContext;
if (typeof docCtx?.registerTool === "function") {
  for (const tool of tools) docCtx.registerTool(tool);
  return "document.registerTool";
}
const navCtx = (nav as HasModelContext).modelContext;
if (typeof navCtx?.registerTool === "function") {
  for (const tool of tools) navCtx.registerTool(tool);
  return "navigator.registerTool";
}
if (typeof navCtx?.provideContext === "function") {
  navCtx.provideContext({ tools });
  return "navigator.provideContext";
}
return "none";

      Mounted once in app/layout.tsx, so every route registers the same set on load. The return value is what the unit test asserts.
    

  


  
Crawler evidence: the form in server HTML

  
This is the exact element captured with curl http://127.0.0.1:4917/ against next start of the built site (HTTP 200, 145135 bytes, one match). It is hidden and aria-hidden, so users and screen readers never meet it, but a reader of raw bytes does.

  


<form toolname="search_docs"
      tooldescription="Full-text search across ALL OrchestKit content (docs, skills, agents, hooks, compositions) via the unified index. Returns matching results with titles and URLs. Optionally filter by content type with `tag`."
      hidden="" aria-hidden="true" data-webmcp="declarative"
      action="/api/search" method="get">
  <label for="webmcp-search-query">Search term</label>
  <input id="webmcp-search-query" name="query" type="search" required tabindex="-1">
  <button type="submit" tabindex="-1">Search OrchestKit docs</button>
</form>

    
ora's recommendation, verbatim: "Register tools with document.modelContext.registerTool() and use navigator.modelContext only as a trailing compatibility fallback. Declarative forms with toolname and tooldescription provide server-rendered evidence, but remain a preview and should not be your only tool surface." The imperative registration above is the primary surface; this form is the evidence.

    Not verified on this page: a real Chrome origin-trial build (149 to 156, shipping targeted 157) invoking the registration end to end. The unit test pins the order with a mocked modelContext; the curl pins the HTML.
