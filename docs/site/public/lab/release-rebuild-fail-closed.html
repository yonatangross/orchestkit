CI FAIL-CLOSED · #4174

The rebuild that reported success

The Rebuild hook bundles on the release PR step in release-please.yml is the one place where main's stale hook bundles get healed before a release ships. It had continue-on-error: true, so even its one existing exit 1 could not fail the job: a rebuild that did not happen reported success.

Before: every exit path, and what it really did

Line (origin/main)ConditionAnnotationExitEffect
281step-level continue-on-error: true--swallows every exit code below; the job can never go red from this step

After: fail closed, with one sanctioned exit 0

FailureAnnotationExit
guard refusal (branch differs outside release-owned paths)::error::1
git fetch / git checkout fail::error::1
npm ci root / npm ci src-hooks / npm run build::error:: naming which1
push fails, remote head UNCHANGED::error::1
push fails, remote head MOVED (a newer run owns the rebuild)::notice::0
no open PR / already current / non-bot author::notice:: / ::warning::0 (unchanged)

The non-bot-author refusal stays exit 0 on purpose: declining to execute a stranger's build script is the guard working, not the rebuild failing. The push-failure arm is the one genuinely ambiguous case, so the step now records the sha it checked out and re-reads the remote head with git ls-remote: a moved head means a newer run owns the rebuild (the step re-runs on every push to main), an unchanged head means the heal truly did not land.

Measured, not asserted

The committed harness tests/ci/test-release-rebuild-fail-closed.sh lifts the step body LIVE from the workflow YAML (the same pattern as tests/ci/test-workflow-step-fault-arms.sh) and runs it against a bare-origin git fixture with PATH shims for gh, npm and git push/ls-remote: five arms, one line each - guard refusal rc1, build failure rc1, push failure with the branch unchanged rc1, push failure with the branch moved rc0 notice, already current rc0.
