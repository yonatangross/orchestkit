Three Builds, One Name

Three workflows each had a job display name of exactly Build. Branch protection required the context Build by name, and GitHub matches required contexts by name alone. A failing build could hide behind another workflow's passing Build.

Before: three jobs, one ambiguous context

Workflow fileJob idDisplay nameLine
.github/workflows/build.ymlbuildBuild21
.github/workflows/ci.ymlbuild-pluginsBuild30
.github/workflows/plugin-validation.ymlbuildBuild26

The required context Build resolved to whichever run reported first. A red build.yml build could pass merge protection whenever ci.yml or plugin-validation.yml reported a green Build on the same commit.

After: one Build, two distinct names

Workflow fileJob idDisplay name
.github/workflows/build.ymlbuildBuild (kept, required context resolves here)
.github/workflows/ci.ymlbuild-pluginsBuild (CI)
.github/workflows/plugin-validation.ymlbuildBuild (Plugin Validation)

Exactly one job named Build remains. Job ids are untouched, so every needs: reference still resolves.

Interim gating until the admin follow-up

Branch protection still lists only Build. Until an admin adds the two new contexts after merge, the renamed jobs stay gated through their aggregators, both of which are required contexts:

  • CI Summary needs build-plugins directly (ci.yml) and its blocking loop exits 1 on a failure or cancellation of that job.
  • Validation Summary (plugin-validation.yml) does not need build directly. It still fails when the build fails: every downstream job needs build without if: always(), so a failed build skips them, and the summary's strict non-success check then exits 1.
Measured on origin/main before the change: 3 jobs named Build, 18 required contexts listing Build. Verify: 1 Build remains, all three YAML files parse, actionlint 1.7.7 exits 0, lab-manifest check exits 0.
