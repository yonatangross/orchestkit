A worktree advisory that no longer falls off the cap

Branch fix/4922-advisory-cap-split, 2026-10-30, issue #4922. The UserPromptSubmit dispatcher sends a pending worktree advisory inside one additionalContext, then deletes the advisory file. Claude Code cuts additionalContext at 8,000 characters or 200 lines without reporting it, so a long advisory lost its tail for good.

1. Size the advisory and the other context

Each advisory line is about 40 characters. Other hooks are held to the effort token budget, so they stay well under the cap on their own; the advisory is the one part delivered past that budget.

BEFORE: send all, delete the file
NOW: send what fits, keep the rest on disk

The rule. Before anything is joined or acknowledged, the dispatcher checks the joined text against both caps. If it would pass either, a part that can keep a remainder (today only the worktree advisory) is shrunk to the room the other parts leave: whole advisories while they fit, then the next one split at a line, with a one-line note that it continues. Acknowledging deletes only the delivered part and rewrites the file with the undelivered lines, so they arrive on the next prompt.

2. The proof

The new dispatcher test writes a 300-line advisory, about 12,000 characters. Before the fix the first prompt carried all of it (past both caps) and the file was gone. After the fix the first prompt stays within 8,000 characters and 200 lines with the file still on disk, and the second prompt delivers the rest: every line exactly once across the two.
