#4136 · the stdin-timeout test raced its own child's boot

runWithDelay(300) started its 300ms write timer at SPAWN, but the child's 100ms stdin window (run-hook.mjs, #3415) opens only after node boots and the bundle loads. Under host load the payload was already buffered in the pipe when the window opened, so the data event cleared the timeout and the WARNS assertion failed. The fix anchors the write to the child's first stderr byte instead of raising the delay.

The three arms after the fix

WARNS
write waits for the first stderr byte, then writes the payload. The warning is already out and stdinClosed is already set, so the late payload is discarded silently. Deterministic at any boot speed.
SILENT
delay 0, unchanged: payload written immediately, buffered before the child even boots, warning must not fire. Negative control against a fix that over-guards.
NEW
regression probe: a test wrapper holds run-hook.mjs back by SLOW_BOOT_MS=250 while the parent delay is 50ms. On pre-fix code the payload lands before the window opens and this test fails.

Two details the fix had to respect

The child HANGS on the empty-payload path: after the 100ms timeout runs the hook, its stdin is still a flowing open pipe, so the event loop never drains. Writing and ending stdin right after the first stderr byte is what lets the child exit, which is why "never write at all" would deadlock rather than be the purest fix.
A child that exits right after writing stderr (failBundleLoad) makes a late write EPIPE. The spawner now swallows EPIPE like the oversized-payload spawner already did, and skips the write entirely when the child has already exited.
