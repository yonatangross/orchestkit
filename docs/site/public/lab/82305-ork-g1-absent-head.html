Who decides whether a missing file was ever there

#4518 taught the standards gate to skip steps 2 and 4 when a PR head lacks configs/standards.json or the baseline, keyed on whether the head also lacked the gate script. CodeRabbit caught the rest: delete all three files and the head still reads as pre-gate. The presence of the file must be proven somewhere the PR cannot touch.

1. The discriminator moves to the base

trusted/ base branch tip the gate code, the only tree anything runs from base/ PR base commit configs only: the floor, AND now the witness head/ PR head DATA ONLY: read as text, never executed

A head file proves nothing either way: the PR wrote the head. The base (pull_request.base.sha) is not PR-controlled. If the base carries the config, a head without it deleted it. If the base lacks it too, the PR lineage predates the gate, like #4513 did.

3. The rule, one line

Each head-side step: [ -f head/<config> ] runs the check; else [ ! -f base/<config> ] skips with a notice (head predates the gate, nothing to widen / raise); else the verdict fails with gate inputs may not be deleted. Step 3 is untouched: the head tree is always judged by floor allowlists and floor baseline.

4. Why the base and not the head script

head-script testdelete configs/* AND scripts/check-frontmatter.py and the head still reads pre-gate; the merge then breaks the gate for every later run
base testthe base is not writable by the PR; a present base config makes a missing head config a deletion no matter what else the head removes
pre-gate stays open#4513 proved a real pre-gate PR carries a pre-gate base.sha, so the skip still fires where it should
bonus correctnessa stale PR that syncs its base onto post-gate main without carrying the configs now fails as a deletion, which is exactly what merging it would do to main
