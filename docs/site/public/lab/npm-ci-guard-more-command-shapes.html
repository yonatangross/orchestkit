The npm ci guard reads more command shapes

A clean install in a worktree whose node_modules is a symlink empties the shared tree the link points at, while printing a normal success line. The guard already denied the plain command. This change teaches it more ways the same install can be written. It stays on the same two files and adds no new hook.

1 / The same commands, on main and on this branch

Each command below was run through the real guard code of main and of this branch, in a working directory whose node_modules is a symlink (unless the row says it is a real directory). Verdicts: deny stops the command, ask puts the question to the person, allow is silent.

2 / What to read in it

RuleChoice
A command it can resolve to a clean install in a linked directorydenied, as before.
A command word it cannot resolve (an unset variable, a substitution)asks, and only where a linked node_modules is at stake. A real directory stays quiet (the row marked real directory).
The new readings share a work budgetpast it the guard keeps its earlier behavior: it asks when the text names a clean install, and never stops quietly.
The new patterns are boundeda long run of unclosed openers or closing parentheses stays linear in the size tests.

Commands such as npm install, git status and eval "$(ssh-agent -s)" are unchanged. Note the row for echo "npm ci": both guards ask when the text names a clean install in a linked directory, so this change leaves it as it was.

What this page does not show

Twenty-seven commands are a sample, not the whole test file: the guard test file holds 327 cases, and the full hooks suite passes. Some commands here were already denied on main, and the rows say so; they are in the sample because they sit in the same families the change reads.
