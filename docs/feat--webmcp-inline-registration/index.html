WebMCP in the served HTML: an inline registration hypothesis test

orchestkit.yonyon.ai registers four WebMCP tools, yet ora.ai scores it 1 of 5 and names only the declarative form. This change puts the same registration in the page source, where ora.ai keeps its own.

Status: a hypothesis, not a fix. Nothing here proves the scanner will credit it. A force:true rescan after deploy is the measurement. If the score does not move, the inline copy is a cheap, harmless fallback and the hypothesis is refuted.

Why the inline copy is the test

ora.ai's own homepage registers its tools in an inline script (var mc = document.modelContext || navigator.modelContext; ... mc.registerTool(tool)). The live layout chunk already carries document.modelContext.registerTool( once, and the scanner still did not credit it. Two readings fit: the scanner reads only inline scripts, or it never fetches that chunk. Both predict the inline copy gets credited.

CSP

next.config.mjs sets script-src 'self' 'unsafe-inline' with no nonce and no hash, and middleware sets no CSP. The inline script is allowed as is. The policy is unchanged; adding a nonce or hash would make browsers ignore 'unsafe-inline' and block the site's other inline scripts.

Checks

  • scripts/check-webmcp-inline-html.mjs (new, wired into docs.yml after the build): reads .next/server/app/index.html and requires the literal inside a <script> with no src. Next's RSC flight payload repeats the string, so flight scripts are skipped and do not count.
  • Planted control: with <WebMcpInlineScript /> removed from the layout the check exits 1; restored, it exits 0.
  • Unit tests run the script text against stubbed globals: registration order, the registry in both orders, the form skip, and a parity test that the inline execute functions fetch the same URLs and return the same results as the chunk tools, including the traversal refusals.

Measure

After deploy, rescan with force:true. Moved above 1 of 5: the scanner reads HTML only, keep both paths. Unchanged: refuted, and the next suspect is the declarative-first ranking in the scanner's own wording.
